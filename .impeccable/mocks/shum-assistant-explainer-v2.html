System Explainer · SHUM Studio · 2026-10-26

SHUM Telegram Assistant

How a Telegram chat becomes the studio's operating system: unstructured messages, voice notes, forwarded portfolios and receipts come in, structured drafts come back for human approval, and only confirmed records reach Google Calendar and the studio's spreadsheets.

01 · Architecture

What runs where

Everything lives on one European VPS behind Caddy HTTPS. Telegram and the studio website push events in through a webhook; the bot, admin panel and background workers share one PostgreSQL database. External APIs are the only things that leave the machine.

02 · Core Pipeline

Any input becomes a reviewable draft

Whatever the team throws into a topic — text, a voice rant, a forwarded conversation, a photo of a poster, a PDF portfolio — the pipeline normalizes it into text, extracts structured fields with an AI model, and shows a draft card. Nothing reaches a sheet or the calendar before a person presses the button.

03 · One Real Path

A forwarded portfolio becomes an HR record

The HR flow is the most demanding path in the system: consecutive forwards are collected automatically, a PDF can take minutes of OCR, and the draft must stay editable without ever double-writing to the sheet. This is the actual production sequence, accepted live on 2026-07-21.

04 · Safety-Critical State

Budget drafts can't be replayed

Money writes get the strictest treatment in the system. A budget draft moves through a small state machine designed so that double taps, webhook retries and Telegram reconnects cannot produce a duplicate expense row.

05 · Cost Control

Every AI call goes through one gate

No feature calls a model provider directly. Avatar prompts, voice transcription, vision enrichment, HR extraction — all of it passes through a single gateway that logs provider, model, function and tokens into one ledger, which is what the admin panel's cost page reads.

06 · What This Buys

The properties that matter

Human control is structural

  • Draft-first everywhere — Calendar, HR, Budget, PR and Client Base all stop at a review card before any write.
  • Access per topic — each Telegram user sees only the functions the owner approved for them.
  • Personal data is read-only — passports and vehicles are shown to two authorized IDs, tap-to-copy, never written.

Built to survive failure

  • Durable batches and drafts — work survives restarts, retries and worker crashes.
  • Webhook self-healing — a 50s handler budget returns 200 to Telegram; 5 clean runs auto-resolve the incident.
  • Non-blocking event loop — all Google I/O runs in worker threads; a slow sheet can't freeze the chat.

Observable end to end

  • 16 error sources, one registry — every domain and worker reports incidents into the same admin surface.
  • Real costs only — the spend page reads the gateway ledger, never estimates.
  • Health on one screen — Postgres, webhook, Google, STT, Vision and OCR workers.
